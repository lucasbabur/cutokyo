## Choose and verify an artifact

Use only an authorized GitHub release. Download the platform archive or an
installer, `SHA256SUMS`, the release manifest, the CycloneDX SBOM, and available
provenance attestation. Compare SHA-256 before execution. Verify the release tag,
repository, artifact name, and platform; a checksum fetched from an unrelated
location is not useful evidence.

The shell, PowerShell, and npm installers are generated by cargo-dist. The npm
package is not a JavaScript implementation: its `node_modules/.bin/cutokyo`
launcher downloads and executes the same native Rust binary as the direct
archive.

## Install the CLI

Follow the command shown on the release page. For npm, install the generated
package into the intended project or global prefix, then resolve the installed
launcher rather than running a repository checkout:

```bash
npm install --save-dev cutokyo@VERSION
./node_modules/.bin/cutokyo --json version
```

For a direct archive, extract it into a private temporary directory, verify the
binary, and move it to a user-owned executable directory on `PATH`. Do not run
an artifact with elevated privileges. `cutokyo --json version` is a liveness
check; it does not mean configuration, storage, or capture are ready.

## First launch

Preview setup before mutation:

```bash
cutokyo --config-file /optional/path/config.toml \
  --data-dir /optional/path/data setup --dry-run --json
```

A dry-run does not create the config file, data root, or log directory. Applying
setup persists a recovery-intent record before external mutation, creates
private owned directories, and writes a versioned default config only when it is
absent. Repeating setup must not duplicate owned state.

```bash
cutokyo setup
cutokyo config list --show-origin --json
cutokyo doctor --json
```

Treat `version` success as process liveness and `doctor` readiness separately.
An unavailable harness can produce an actionable capability outcome while the
process remains alive.

## Platform paths

Without explicit flags or environment variables, Cutokyo uses the operating
system's native per-user config and data roots through the `directories` crate:

- Linux follows XDG config/data conventions;
- macOS uses the user Application Support/config conventions selected by the
  platform API;
- Windows uses the corresponding per-user known folders.

`CUTOKYO_CONFIG_FILE` and `CUTOKYO_DATA_DIR` override those locations; explicit
CLI flags win over environment values. Only one config file is read. Run
`config list --show-origin` to see defaults, file, environment, and CLI
candidates for every setting.

Do not place the database on a network filesystem or cloud-synchronized folder.
Keep full-disk encryption enabled because `0.x` has no application-level
database encryption.

## Upgrade and downgrade

Before upgrade:

1. drain the spool;
2. run `doctor` and save only a reviewed diagnostic bundle if needed;
3. create an online backup with `cutokyo backup`;
4. verify its receipt;
5. install and checksum the new artifact;
6. rerun `version` and `doctor`.

Database migrations are forward-only. A newer binary may migrate an older
schema; an old binary refuses a newer schema rather than opening it best-effort.
Derived projection version changes rebuild derived data. Every released spool
format remains readable. Keep the verified pre-upgrade backup and binary until
the new version passes integrity and readiness checks.

## Desktop installation

Desktop bundles are separate platform artifacts. macOS packages require
Developer ID signing and notarization, Windows packages require Authenticode,
and updater payloads require Tauri updater signatures. Linux artifacts are
checksummed and attested but do not acquire platform code-signing semantics by
association.

After install, start the package-installed application—not a development binary.
The Linux release smoke resolves the sole `/usr/bin` executable from the installed
Debian package database, then invokes that exact file with
`--cutokyo-probe-liveness` (expected exit 0) and
`--cutokyo-probe-readiness` (expected exit 69 for a fresh, unconfigured home). It
then removes the package, proves the executable is gone, and repeats removal to
prove idempotence. These package-only probes never activate the GUI and never use
a checkout or `target/` fallback.

For an ordinary installation, confirm that a process appears, then verify product
readiness through the same health surface as `cutokyo doctor`. The release
workflow's Linux smoke evidence does not claim that macOS or Windows packages
executed; their signed artifacts have their own release gates.

## Uninstall

Run the application use case before removing the executable:

```bash
cutokyo uninstall --json
```

Uninstall is repeatable. Missing or already-removed owned setup state is a
successful no-op. It removes only identifiable Cutokyo-owned setup metadata and
must preserve the configuration file, database/history, neighboring user-owned
entries, and unrelated harness configuration. A never-activated install must be
removable without inventing recovery state.

Delete retained history or the config/data roots only as a separate deliberate
action after reviewing backups and the deletion limits in
[`privacy.md`](privacy.md). Removing package files is not secure data erasure.

## Recovery

If setup or uninstall is interrupted, do not manually delete its recovery
record. Preserve the target files, run `doctor`, and retry the same operation.
Atomic writes recheck the source bytes before publication so a concurrent user
edit wins instead of being overwritten. Symlink and non-regular targets are
refused.

For a failed release installation, restore the previously checksummed binary and
follow [`release/recovery.md`](release/recovery.md). For support, share the
command, safe error code, doctor output, versions, and a reviewed diagnostic
bundle—not raw history or database files.
